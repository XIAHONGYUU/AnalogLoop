# 架构

## 设计立场

这个架构不是“让 LLM 设计电路”，而是**让 LLM 管理一个实验**。由此得到四条立场：

1. **策略与机制分离。** LLM 决定“试什么、为什么、何时停”；执行由确定性代码完成。
2. **仿真器是唯一真值。** 代理模型可以快，但不能替代签核。
3. **记忆是一等公民。** 事实、启发式、代理模型、失败原因分开存储。
4. **预算是控制信号。** 每次评估都要记账，预算控制器可以否决策略层的请求。

## 五个模块

### ① 目标与约束

输入不是一句自然语言，而是一份可检查的 spec：

- 设计目标：Gain、UGB、PM、Power、Noise、Offset、Slew Rate 等；
- 约束：电源、负载、面积、摆幅、输入共模；
- 参数空间：可调变量、范围、步进、整数/离散约束；
- PVT：角落、温度、电源容差；
- **可行性预检**：用设计方程或 gm/ID 粗算，先判断 spec 是否落在可实现区间。

可行性预检很便宜，却能避免在空设计空间里烧仿真。

### ② 策略层（LLM）

LLM 的职责被刻意限制为四件事：

- 理解 spec 与拓扑，选择搜索策略（DoE、BO、局部搜索、随机重启）；
- 读取失败信息，提出下一步假设；
- 在预算约束下决定“继续 / 换策略 / 停”；
- 把成功与失败总结成可审核的文字，写入知识库。

**不做**：数值插值、梯度计算、矩阵求解、记忆数值状态。这些交给工具链和账本。

### ③ 工具链（确定性）

工具链是 agent 与物理世界之间的唯一通道：

- 渲染 deck / 测试台（模板 + 参数，不让 LLM 直接写任意 SPICE）；
- DoE、BO、局部搜索、successive halving；
- 调用快速代理；
- 运行 SPICE（通过适配器）；
- 测量与结果解析（measurement contract）；
- 写 case 账本；
- 生成报告与图。

工具必须满足：**typed、白名单、幂等、可审计、有成本字段**。详见 [tool-contract.md](tool-contract.md)。

### ④ 验证层（两种速度）

- **4a 快速代理**：gm/ID 表、器件级代理、电路级 GP/NN；输出预测值、不确定度、OOD 分数。
- **4b 真实 SPICE**：ngspice / HSPICE / Spectre；输出测量值、原始文件哈希、仿真器版本。
- **晋级门**：决定候选走哪条路，以及是否需要抽样复核。

详见 [fast-verification.md](fast-verification.md)。

### ⑤ 记忆与知识

四类存储，生命周期不同：

| 存储 | 内容 | 可信度 | 用途 |
|---|---|---|---|
| Case 账本 | 每次评估的输入/输出/版本/哈希 | 高（事实） | 重放、审计、训练 |
| 技能/规则 | “先调第二级电流”这类启发式 | 中（可错） | 策略提示 |
| 代理模型 | 表、GP、NN 及其训练集哈希 | 中（有分布） | 快速评估 |
| 负知识 | 失败原因、不可行区域 | 中（需复核） | 避免重复踩坑 |

## 两条回路

- **内环**：单条 case 内，“提出候选 → 评估 → 测量 → 修正”。
- **外环**：跨 case，“用历史结果修正目标、约束、策略、代理”。

两条回路分开的好处是：内环可以很快，外环可以很慢；内环的错误不会直接污染目标，外环的修改必须经过人工或规则审核。

~~~mermaid
flowchart LR
  A[目标与约束] --> B[策略层 LLM]
  B --> C[工具链]
  C --> D{晋级门}
  D -->|快路径| E[快速代理]
  D -->|慢路径| F[真实 SPICE]
  E --> G[记忆与账本]
  F --> G
  G -.->|内环| B
  G -.->|外环| A
  H[预算与晋级控制器] -.-> B
  H -.-> C
  H -.-> D
~~~

## 一次迭代的数据流

1. 策略层读取 spec、当前最优、最近失败、剩余预算。
2. 策略层调用 `propose_candidate`，给出候选与理由（不写网表）。
3. 工具链做静态检查：参数范围、拓扑连接、测试台端口、角落完整性。
4. 晋级门决定：快路径 / 慢路径 / 两者都跑。
5. 快路径返回 `(mu, sigma, ood)`；慢路径返回测量值与原始文件哈希。
6. 工具链写 case 记录，更新账本与代理误差模型。
7. 预算控制器更新剩余预算；若触发停机条件，返回 `stop`。
8. 策略层读取新状态，进入下一轮。

## 为什么 LLM 要“无状态”

LLM 的上下文不是数据库：

- 它会被截断、被摘要、被幻觉污染；
- 它记不住精确的数值和版本；
- 它倾向于把“最近看到的”当成“最重要的”。

把状态放在账本里，LLM 每轮只读取一个**受控视图**（当前最优、最近失败、预算、约束）。这既降低 token 成本，也让重放成为可能。

## 为什么工具链要“确定性”

- 同一个候选必须得到同一个 deck；
- 同一个 deck 必须得到同一个测量；
- 同一个测量必须能追溯到仿真器版本和模型哈希。

如果工具链本身是随机的，代理误差、策略效果、重放都无法区分。

## 失败模式

| 失败 | 表现 | 对策 |
|---|---|---|
| 代理外推 | 预测很好，SPICE 很差 | OOD 检测 + 强制 SPICE |
| 角落遗漏 | TT 过，SS 挂 | corner-aware 采样 + 最差角落门 |
| 指标刷分 | PM 刚好 60°，但启动失败 | measurement contract + 多指标门 |
| 账本污染 | 旧版本结果混入 | schema + 版本哈希 + 只追加 |
| LLM 幻觉 | 编造器件参数 | 工具白名单 + 参数范围检查 |
| 预算耗尽 | 没找到可行解 | 早停 + 可行解优先 |
| 版本漂移 | 代理/仿真器升级后结论失效 | 全链路哈希 + 回归集 |

## 与经典 agent 架构的差异

经典 ReAct agent 是“想 → 调工具 → 看结果 → 想”。这里多了三样东西：

1. **预算控制器**：工具调用有价格，策略层不能无限试。
2. **晋级门**：不是所有评估都值得用真值。
3. **账本**：状态外置，可重放，可训练。

这也是它更像“实验管理系统”而不是“聊天机器人”的原因。
